## 實作方向

使用者已確認日常使用比特瀏覽器。優先使用安裝在該比特瀏覽器環境內的助手，沿用使用者已登入的健康優選與賣貨便工作階段。健康優選負責訂單校驗、批次保留及結果回寫；瀏覽器助手負責跨網站的匯入步驟。登入失效或身分驗證時，暫停並顯示需要處理的項目。

比特瀏覽器官方確認可透過擴展中心添加本地 Chrome 擴充套件：https://www.bitbrowser.cn/blog/rhzbtllqtjxdkz_ 。首次安裝需完成後在實際使用的瀏覽器環境驗證；不把這項平台能力當成本助手已完成或相容性已測試。官方亦提供 Local API，但目前不需要開放對其他瀏覽器環境的控制權。

若確認帳號已有正式 API，改用正式 API 可減少介面維護。不優先把帶有登入工作階段的瀏覽器放到 Vercel；雲端排程也不在目前已確認範圍內。

## 操作流程

1. 在後台選取指定賣場的可處理訂單並發起自動轉單。
2. 先檢查助手、健康優選登入、賣貨便登入及匯入頁是否就緒，再保留批次。
3. 沿用既有官方 XLSM 產生器，以檔案內容傳給助手；不要求使用者到下載資料夾找檔案。
4. 核對登入的賣家與本次目標、頁面及待送批次，匯入一次。
5. 取得該次匯入結果；以健康優選原單號對應，並核對收件人、手機、門市、商品及金額。不能依行號、姓名或出現任意 CM 編號就判定成功。
6. 每筆確定成立的訂單沿用資料庫原子確認操作，保存賣貨便編號並更新已出貨；失敗或結果不明的保留待處理。
7. 顯示成功、失敗、需人工接手的筆數與原因。

## 中斷與重複操作

- 提交前失敗可恢復；提交後回應遺失、重新整理或助手重啟時，先恢復該次結果，禁止盲目重送。
- 原訂單的唯一批次保留由伺服器持久保存；助手只准為未保留的訂單建立全新批次，不提供用舊批次重傳的入口。本機提交狀態在檔案事件前保存。即使本機資料被清除，伺服器既有保留仍會阻止新任務重傳原訂單，無需擴增資料庫結構。
- 延用批次唯一性、原始快照、外部編號唯一性及確認回寫冪等性；下載完成不能解除保留。
- 結果不明不自動解除保留；部分成功只回寫有完整成功證據的項目。
- 助手只取得本批作業所需資料，不讀取或上傳登入密碼、Cookie、無關分頁或瀏覽紀錄。

## 0.2.1 連線修正

使用者在比特瀏覽器安裝 0.2.0 後，工作台顯示「助手處理失敗」，轉單按鈕尚未啟用。已確認原介面會把沒有 ok/error 的空白背景回覆轉為此泛用錯誤；尚未直接觀察比特瀏覽器內的根本原因。

修正以 callback 呼叫 Chrome API、在 callback 內讀取 lastError，保留非同步 sendResponse 的 return true 模式；對工作台同時驗證訊息來源網域、主框架及瀏覽器目前網址，避免僅以頁面切換前的 sender.url 路徑拒絕合法連線。新版驗證狀態結構，顯示版本與可操作的連線錯誤，斷線時停用轉單。沒有新增權限或訂單操作。

新增7項測試覆蓋舊文件網址、callback-only 介面、外站／子框架／分頁離開工作台、Chrome lastError、空白回覆與狀態結構。這些是本機模擬驗證，仍需使用者更新原擴展並重新開啟比特瀏覽器環境後確認。

## 0.2.2 匯入路徑修正

使用者後續截圖已確認0.2.1成功連線，仍出現找不到可用匯入頁；隨後提供真正網址 https://myship.7-11.com.tw/orderimport/import 。原先依較早環境資訊採用 /seller/order/*，沒有涵蓋實際頁面，導致腳本不會載入、分頁搜尋找不到、上傳與結果讀取網址檢查也會拒絕。

0.2.2同步補上 /orderimport/*，保留既有路徑相容性。分頁搜尋仍先做只讀的完整頁面檢查，沒有唯一可用匯入頁時不能保留批次或上傳。現在保留每個頁面檢查失敗的具體原因，缺少腳本時明確要求重新整理賣貨便分頁。新增7項路徑、權限與錯誤訊息測試，既有模擬上傳測試改採實際網址，合計518項測試通過。

公開未登入的網址查閱只返回會員登入提示，不能據此判定使用者已登入的比特環境失效。實際DOM、上傳及下載仍待首筆驗收；本輪沒有操作真實訂單。
