# 賣貨便轉單工作台 Implementation Plan

**Goal:** 在既有後台整理待確認訂單、產生官方 v1.4 XLSM 匯入檔，並於管理員核對賣貨便成功編號後原子回寫已出貨。

**Architecture:** Next.js API 沿用管理員驗證，增加專用 orders.transfer 權限。Supabase 保存規格賣場配對與不可重複的轉單紀錄；資料庫函式鎖定訂單、核對快照，避免同時匯出與中斷重送。官方模板保留全部原始 OOXML 部件（包括巨集，但不執行），僅加入資料列。此階段不包含尚未觀察到的賣貨便上傳及結果介面。

**Tech Stack:** Next.js 14、TypeScript、PostgreSQL、fflate。

## Task 1：範本規則與匯出
- 建立 `lib/myship/domain.ts` 與 `lib/myship/workbook.ts`。
- 按 v1.4 規則驗證：500筆、姓名長度、手機、6碼門市、常溫/冷凍、商品及備註長度、代收55~20000。
- 金額使用原訂單總額，運費先明確設定0（不額外向客戶加收），僅處理已配對的同賣場訂單。
- 保存原始範本到 `assets/myship/order-import-v1.4.xlsm`，鎖定 SHA256。
- 測試前導零、文字 XML 跳脫、公式字串、金額、規格組數、未知賣場、多賣場、檔案原始部件完整性。

## Task 2：持久化及原子操作
- 建立 `migrations/myship_transfer.sql`，包含賣場、規格配對、轉單快照。
- 以訂單唯一鍵及資料庫鎖保證一次保留，同一批次衝突整批回滾。
- 匯出後只進入 exported；確認外部訂單編號後，於單一交易中保存編號及更新已出貨。
- 取消或內容改變時拒絕回寫。RLS 啟用，RPC 僅 service_role 可執行。

## Task 3：API與工作台
- 建立 `app/api/admin/myship` 的預覽、規格配對、匯出與確認端點。
- 建立 `app/admin/myship/page.tsx`，沿用後台表格樣式、提供每筆錯誤、批次下載和人工確認入口。
- 更新後台導航與權限清單。所有寫入端點檢查權限、同源與輸入大小。
- 下載失敗可重新下載原批次，不能因此建立新批次。

## Task 4：驗證與交付
- 執行新增測試、TypeScript、現有檢查及建置，區分既有失敗與新問題。
- 用合成資料驗證 XLSM，禁止用真實客戶做未授權測試訂單。
- 保存差異檔和部署說明。資料庫遷移及正式部署留至可檢視的程式完成後；不直接修改線上訂單。
- 自動上傳與自動結果回讀仍需實際匯入頁及结果格式，不能稱為已完成全自動。
