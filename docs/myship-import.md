# 賣貨便轉單工作台

健康優選後台 `/admin/myship` 提供官方 v1.4 XLSM 產檔、結果檔逐欄核對及出貨回寫。比特瀏覽器助手目前為 0.2.4，包含自動傳檔、匯入、結果回讀與中斷恢復。使用者已確認0.2.1連線成功，並提供真正匯入頁 https://myship.7-11.com.tw/orderimport/import；0.2.2補上此前漏掉的網址範圍。使用者已確認自動匯入成功。0.2.3依實際頁面原始碼支援結果下載按鈕，自動讀取及回填仍待瀏覽器驗收。

0.2.1 修正空白背景回覆未診斷的問題，改用 callback 相容介面，並同時核對傳送者來源及瀏覽器目前分頁網址，支援從其他後台頁面切入工作台。後台顯示助手版本，連線遺失時停用轉單按鈕。更新原資料夾及原擴展項目以保留作業狀態；詳見助手 README。

0.2.2 在安裝設定、分頁搜尋、上傳及結果讀回加入 `/orderimport/*`，並保留既有 `/seller/order/*`。匯入前仍需確認唯一檔案欄位、未選檔及唯一可用頁面。現在會保留頁面檢查的具體原因，區分沒有分頁、腳本未載入及欄位檢查失敗。

## 0.2.4 阻塞恢復

助手遇到需要核對的批次，可按「保留此批，繼續其他訂單」，伺服器原訂單保留不會解除。舊批次仍在批次紀錄中，不能重傳同一訂單。

`migrations/myship_confirm_recovery.sql` 需另行在資料庫執行：支援原单已出貨且僅狀態與更新時間不同時補記成功編號，保留CM唯一性與完整其餘資料核對。僅部署網站不會套用此資料庫規則。

## 自動轉單與结果回讀

在後台下載助手，按安裝包內說明加入比特瀏覽器。健康優選及賣貨便需在同一個環境登入，先開啟乾淨的賣貨便訂單匯入頁，再在健康優選選取1筆並按「自動轉到賣貨便」。首筆成功後才開放多筆操作。

助手不落地下載中間檔；上傳前先在伺服器保留原批次，且保存本機提交狀態。任何中斷都不會自動重新提交；「讀回上一批結果」只取結果並重試冪等回寫。已支援 /orderimport/result/16位編號 的官方結果下載按鈕。若遇到尚未支援的按鈕型態，助手會停止並留下原因，不冒充成功。

已手動匯入的批次，可在「批次紀錄」選擇「讀取本批結果檔並更新已出貨」，直接使用賣貨便下載的結果。系統先核對所有原單號、完整收件資料、商品、金額及唯一 CM 編號，再呼叫原子回寫。未知欄位、錯配或重複編號會拒絕；結果中缺少或沒有有效成功編號的訂單保持待處理。

11欄結果格式已用使用者提供的真實結果檔讀取驗證，並与原始批次逐欄比對一致。驗證過程未修改正式訂單。詳見 `extensions/myship-assistant/README.md`。

## 保留的手動匯入流程

1. 開啟「賣貨便轉單」，首次使用先在「商品賣場配對」指定每個商品規格的所屬賣場。目前僅啟用 `GM2601252733206`。另一賣場、未配對商品及跨賣場混合訂單不能匯出。
2. 在「待處理訂單」選取可匯出的訂單，按「建立並下載匯入檔」。一份檔案最多 500 筆；超過時分批。姓名、手機、6 碼門市店號、商品規格、組數與金額會自動填入。
3. 在賣貨便賣家後台使用訂單匯入功能上傳檔案，依實際頁面完成驗證及成立訂單。範本本身提供 Excel「驗證」功能；本程式保留但不執行其巨集。平台是否要求先執行該驗證，仍需實際匯入測試確認。
4. 匯入成功後，到「批次紀錄」核對收件人、商品、門市及代收金額，填入 `CM` 開頭的賣貨便訂單編號，再按「記錄並更新已出貨」。系統在同一筆交易中保存外部編號並把原訂單改為「已出貨」。

單純下載或上傳檔案不等於訂單成立，因此匯出時仍保持「待確認」。正常處理不需要逐筆到賣貨便搜尋重複訂單；系統只利用自己的轉單紀錄避免重複匯出。

## 金額與資料規則

- F 欄為原網站訂單總額，G 欄運費固定為 `0`，代收總額不額外加價。這是此工作流程的收款設定，不表示物流服務免費。
- 商品欄保留 SKU、商品名稱、規格與組數，例如「3袋 ×1」表示一組三袋。
- 店號取自 `stores_711.store_code`，並核對原訂單保存的門市名稱及地址；不能用門市名稱代替 6 碼店號。
- 不截斷姓名、備註或商品；不猜測缺失門市或賣場。不符合範本限制的資料會顯示原因。
- 原訂單號放在「其他資訊」，方便在賣貨便核對。
- 範本沒有獨立賣場 ID 或商品 ID 欄位。因此本版配對用於分流檔案，尚未證明匯入會綁定該賣場商品、同步庫存或自動扣庫存。

## 中斷與失敗

- 下載中斷：到批次紀錄重新下載原批次。若任何一筆已確認或解除，整批不能重新下載。
- 匯入結果不明：保留原紀錄，先查明是否成立，不直接重匯。
- 明確未匯入或失敗：在核對視窗展開「未匯入或明確失敗」，確認未成立且不再使用原檔，填寫原因後解除保留。修正資料後可重新匯出，原歷史仍保存。
- 匯出後原訂單被修改或取消：系統拒絕直接回寫出貨，需先人工核對兩邊資料。
- 已成立的外部訂單無法由本功能取消；解除保留也不會取消任何賣貨便訂單。

## 部署與驗收

部署時先確認資料庫遷移成功，再發佈網站程式；以下步驟供後續環境重建與驗收使用。

1. 在隔離的 Supabase 測試專案執行 `migrations/myship_transfer.sql`。依賴既有 `orders`、`order_items`、`product_variants`、`stores_711` 和管理員系統。
2. 沿用專案原有 Supabase 環境變數及正式 `JWT_SECRET`，不要把服務端金鑰放到前端或 Git。非超級管理員需授予 `orders.transfer` 權限並重新登入；`all` 權限可直接使用。
3. 安裝鎖定依賴，部署時需包含 `assets/myship/order-import-v1.4.xlsm`。Next 的檔案追蹤已涵蓋批次建立與下載端點。
4. 在測試環境以合成訂單檢查工作台：商品配對 → 匯出 → 中斷重新下載 → 核對成功 → 出貨回寫；亦驗證缺少店號、跨賣場、訂單取消、金額改變和解除保留。
5. 以經核對的一筆真實待處理訂單做賣貨便匯入驗收，確認檔案接受、代收額、商品與門市，並觀察實際成功編號格式。不要上傳測試收件人到正式賣貨便。上線前也需確認之前已手動完成的訂單已更新狀態。
6. 助手已實作使用者點擊後的自動上傳與結果回讀。實單驗收仍須確認賣家歸屬、實際上傳欄位及結果下載方式；目前沒有自動登入或背景排程。
